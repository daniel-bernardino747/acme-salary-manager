**Question 2: how is the average rounded to a whole minor unit?**

**My recommendation:** take the exact sum of the minor units, divide by the headcount, and **round half up**. Because every salary is positive, half up and half away from zero are the same thing. Use integer arithmetic only: `floor((2·sum + n) / (2·n))`. No float ever touches the result.

**Question 3: how are rates stored?**

**My recommendation:** a **scaled integer**, quoted the way rates are published: **local currency units per 1 USD, to 6 decimal places**. For example INR 83.123400 is stored as `83_123_400`, EUR 0.921500 as `921_500` and USD as `1_000_000`. Each currency also records its ISO 4217 minor-unit exponent (JPY 0, the rest 2).

Conversion: `usdMinor = roundHalfUp(localMinor · 10^(2 − exp) · 10⁶ / rateScaled)`, using the same quotient-and-remainder rule.

**Why scaled integer over numerator/denominator:** it matches the published rate a reader checks against, there's one number per currency, and a fixture is a one-line hand calculation. Numerator/denominator can be exact for any rational rate, but published rates are already decimals, so the exactness buys nothing.

**One honest catch:** the product overflows. A ₹50 crore total is 5·10¹³ paise, and times 10⁶ that's 5·10¹⁹, past 2⁵³. Every representation hits this. So **the conversion function computes in BigInt internally** and returns a number, after asserting the result is a safe integer. BigInt stays inside that one function, and the rest of the money code uses plain numbers.

Do you agree?
