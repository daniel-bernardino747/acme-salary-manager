**Q1. Where are pay statistics computed?**

**My recommendation: (b).** SQL only selects and filters rows. Pure domain functions compute every statistic: min, max, median, average, headcount, payroll totals, USD conversion and compa-ratio. Each pay question becomes one narrow query (e.g. `SELECT salary_minor FROM employees WHERE job_title = ? AND country = ?`, or `SELECT country, department, salary_minor` for payroll), and its result is passed to a domain function.

**Why:** ADR 0001's rules don't fit SQL well:
- round half up once per result, with integer quotient and remainder
- the median "as shown", which feeds the compa-ratio test
- per-currency subtotals converted once through BigInt
- the outlier boundary checked by cross-multiplying

If SQL computed any of these, we'd have two implementations of the same rules, and the hand-computed fixtures would only test one of them. With (b), every rule lives in one place that tests can reach with no database.

The cost is small. The heaviest query, for outliers, reads at most 10,000 rows of `(id, title, country, salary)`. In SQLite that's a few milliseconds, well inside the 500 ms target.

**What I'd reject:**
- **(a) SQL aggregates plus a window-function median.** The rounding and the median would live in SQL, outside the pure fixtures.
- **(c) a mix.** For example, `SUM … GROUP BY currency` in SQL. It saves almost nothing at this volume, and it splits one rule across two layers.

**Q4. Should name search ignore accents and case beyond ASCII?**

SQLite's `LIKE` ignores case only for ASCII letters. So a search for "muller" won't find "Müller", "joao" won't find "João", and "ÖZ" won't match "öz". With employees in Germany and Brazil, the seed will probably include names like these. (Japanese and Indian names will most likely be romanized, which is the seed ticket's call.)

**My recommendation:** add a derived column, `name_search TEXT NOT NULL`, written by the repository on every insert and update. Its value is the name normalized to NFD, with combining marks removed, then lowercased.
