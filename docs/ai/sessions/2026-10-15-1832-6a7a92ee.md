**Q3: Listing, search, filters and sort**

**My recommendation:**
- **Page-based pagination:** `page` counts from 1 and defaults to 1. `pageSize` defaults to 25 and has a maximum of 100. The response looks like `{ items, page, pageSize, total }`. A page past the end returns 200 with empty `items`. A page size of 0 or more than 100, or a non-integer, is a 400.
- **Search:** `q` is the per-word prefix match from ADR 0002. It is trimmed, an empty or whitespace-only value means no search, and its maximum length is 100 characters.
- **Filters:** `country`, `department` and `jobTitle` each take one optional exact value from the reference lists, and they combine with AND. An unknown value is a 400, as you said.
- **No sort parameter.** The order is fixed at `name, id` (ADR 0002 already indexes for it). HR looks people up by name and the filters do the narrowing, so a sortable column would add a parameter and index decisions with no question that needs it.
- **Strict query schemas:** an unknown parameter is a 400, so a typo such as `?contry=IN` isn't silently ignored.
- **`/api/outliers` uses the same envelope and filters.** Two details follow from your adjustment:
  - **"Most extreme" means the furthest from 1.00 in either direction**, so 0.70 and 1.30 rank the same. The comparison is exact: `|s₁−m₁|·m₂` against `|s₂−m₂|·m₁`. That product can exceed 2⁵³ (INR salaries in paise times a median), so it uses BigInt inside the domain function, the same way conversion does. Ties order by `name, id`.
  - **It paginates in memory.** Being an outlier is decided by the domain, not by SQL. So the service reads the filtered rows (all of each peer group that the filters touch), the domain ranks every outlier, and the service slices out the page and counts the total. The peer groups must be complete even under a department filter, because the median is over the whole peer group, not just one department.

**Alternatives:**
- **Cursor pagination:** rejected. The UI wants page numbers and a total, and an offset over about 10,000 rows on the `(name, id)` index is cheap.
- **Multi-value filters** (`?country=IN&country=BR`): not in the requirements. You can add them later without breaking anything.

The last point in the outliers bullet is a correctness trap: filter by department before grouping and the medians come out wrong. Do you agree the filters only narrow which outliers are *shown*, never which employees the median is computed from? Accept, or adjust?

**Q4: Validation mechanics and the error format**

**My recommendation:**
- **A small custom `ZodValidationPipe` in `api`**, about 20 lines, applied per parameter: `@Body(new ZodValidationPipe(CreateEmployee))` and `@Query(new ZodValidationPipe(EmployeeListQuery))`. The same schema objects are what the UI form validates against. `:id` gets a schema too (a positive integer, otherwise 400).
- **Errors use RFC 9457 Problem Details** (`application/problem+json`), produced by one global exception filter:
  ```json
  { "type": "about:blank", "title": "Validation failed", "status": 400,
    "detail": "Request body is invalid",
    "errors": [{ "path": ["annualSalary", "amountMinor"], "message": "Must be greater than 0" }] }
  ```
  The `path` values are the Zod issue paths, so the UI can attach each message to its form field without a mapping table. The schema for this error body lives in `@acme/contract` too.
- **Status codes:** 400 for any request that fails its schema, query or body. 404 for an unknown employee. 500 is a generic problem body with no stack trace or SQL in it, and the detail is logged on the server.
- **Responses are not parsed at runtime.** Services are typed with `z.infer` at compile time, and the HTTP tests parse every response with its response schema. The contract is enforced at the test seam, and production doesn't spend time re-validating its own output.

**Alternatives:**
- **The `nestjs-zod` library:** it buys DTO classes and Swagger integration, but we've ruled out OpenAPI, and it's one more dependency to track Nest and Zod releases for 20 lines of code.
- **`class-validator` DTOs:** rejected. That is a second schema language beside Zod, which is the drift this ticket is avoiding.
- **422 for body validation and 400 for malformed requests:** a defensible split, but the UI handles both the same way. One status keeps the rule and the tests simple.

Accept, or adjust?
