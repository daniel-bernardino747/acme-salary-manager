**Q2. Data fetching, and how the list and stats refresh after an add, edit or delete**

**My recommendation: TanStack Query v5, with every employee mutation invalidating every query.**

- **Invalidate everything on success.** Any add, edit or delete calls `queryClient.invalidateQueries()` with no key. Every query in this app (the list, a view, all four questions) is derived from the employees table, so any mutation can make any of them stale. A targeted key map, such as "an edit to an IN Software Engineer only touches these stats," is logic we'd have to test and could get wrong. Invalidation only refetches the queries currently on screen; the rest are marked stale and refetch when visited. That meets the requirement "add, edit or remove updates the list and the stats" by construction.
- **No optimistic updates.** Each write takes one round-trip under 500 ms. Rollback logic isn't worth it here.
- **Query keys** are `[resource, params]`, e.g. `['employees', { page, q, country }]` and `['pay-statistics', { jobTitle, country }]`.
- **Paging** uses `placeholderData: keepPreviousData`, so the table doesn't flash empty between pages.
- **Defaults:** `staleTime` of 30 s, and `retry` off for 4xx.
- **One `apiFetch` wrapper:**
  - It sends JSON and returns the typed body (`z.infer` types from `@acme/contract`).
  - On a non-2xx response it throws an `ApiProblem` that carries the parsed Problem Details. Q5 uses those to map form errors.
  - It doesn't parse successful responses with Zod at runtime, matching ADR 0003's stance. The HTTP tests guard the shapes.
- **Rejected:**
  - **SWR:** weaker mutation and invalidation story.
  - **RTK Query:** brings Redux for no reason.
  - **Plain `useEffect` fetches:** we'd rebuild caching, race handling and refetching by hand.
